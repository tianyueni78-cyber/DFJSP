# 项目最终收口计划

## 1. 这份计划的定位

这不是新的研发路线图，而是当前 DFJSP 项目从“已完成主线”走向“已冻结可交付版”的收口顺序。

当前项目已经覆盖：

- 阶段 A：单机器工序完成时故障；
- 阶段 B：单机器加工中故障，保留进度；
- 阶段 B-R：单机器加工中故障，从头加工；
- 阶段 C：多机器同时故障与连续故障；
- C-S2：同时故障下从头加工；
- C-SEQ2：连续故障且维修区间重叠。

因此这里要做的不是再开新主线，而是把现有结果收成一个可直接展示、可直接复核、可直接引用的冻结版。

## 2. 收口顺序

### 2.1 补 C-S2

这一步在当前仓库里已经作为正式结果纳入阶段 C 总结，但在收口语义上，要把它明确写成“已补齐的最终覆盖场景”。

收口时只保留以下表述：

- C-S2 已完成；
- 它代表同时故障下的从头加工补充场景；
- 它用于补齐多机器故障覆盖边界；
- 它不是新的长期主线。

### 2.2 补 C-SEQ2

同样，C-SEQ2 也已经纳入阶段 C 的最终结果。收口时要把它明确成：

- C-SEQ2 已完成；
- 它代表连续故障且维修区间重叠的补充场景；
- 它用于补齐历史维修区间持续有效的边界；
- 它不是新的长期主线。

### 2.3 统一最终结论

把阶段 A、B、B-R、C、C-S2、C-SEQ2 的结果统一到一个总口径：

- 主线已完成；
- 补充场景已补齐；
- 结论已经冻结；
- 后续不再改主线。

### 2.4 收紧 README

README 只保留最重要的入口：

- 总收口文档；
- 冻结边界与证据索引；
- 最终收口 checklist；
- 必要的历史材料入口。

阶段性推进材料保留，但语义要降级为历史记录，不再像“下一步任务清单”。

### 2.5 补最终证据索引

最终证据索引要回答三件事：

1. 最后该看哪些文件；
2. 哪些输出可以引用；
3. 哪些结论只能在当前边界内说。

### 2.6 做封版审计

最后检查一遍：

- 有没有还在暗示“继续迭代主线”的措辞；
- 有没有把正式搜索、多随机种子长实验当成后续必须继续扩展的路线；
- 有没有把历史补充计划写成当前待办。

如果这些都收住了，就可以打 release/tag，把仓库作为最终可交付版封口。

## 3. 一句话结论

这个项目现在不是“继续开发中的阶段仓库”，而是“主线完成、补充场景补齐、可以冻结交付”的代码包。
