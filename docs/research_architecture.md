# FJSP-AGV 动态事件重调度研究架构

## 1. 总课题

本项目研究正常 FJSP-AGV 调度方案执行过程中发生动态事件后，系统如何识别受影响任务、保留已经执行的生产状态，并生成新的调度方案。

总课题暂定为：

> FJSP-AGV 系统中的动态事件响应与重调度

当前研究两个大课题：

```text
动态事件重调度
├── 课题 A：机器故障
└── 课题 B：订单撤销
```

机器故障和订单撤销是两类不同的动态事件，但可以共享状态提取、剩余问题构造、重调度策略和评价框架。

## 2. 研究层级

为了避免概念混乱，研究内容分为五个层级：

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| 动态事件类型 | 发生了什么变化？ | 机器故障、订单撤销 |
| 事件场景 | 事件以什么形式发生？ | 单机器故障、多机器同时故障 |
| 受影响对象 | 哪些任务需要处理？ | 中断工序、未开始工序、被撤销订单 |
| 重调度策略 | 调整多大范围？ | 直接修复、局部优化、全局重调度 |
| 评价指标 | 调整结果是否更好？ | 完工时间、能耗、计划扰动、运行时间 |

其中：

- 单机器故障、多机器故障属于“事件场景”。
- 局部优化、全局重调度属于“处理策略”。
- 二者不是同一层级，可以组合形成不同实验组。

## 3. 课题 A：机器故障

### 3.1 研究问题

机器在原调度方案执行期间不可用时，如何处理正在加工和尚未开始的任务，并重新安排机器与 AGV。

### 3.2 故障场景

机器故障分为三个逐步扩展的子问题：

```text
A1：单机器故障
A2：多机器同时故障
A3：多机器连续故障
```

#### A1：单机器故障

一次只有一台机器发生故障。用于建立和验证最基本的故障处理流程。

需要描述：

- 故障机器编号
- 故障开始时刻
- 维修时长或修复时刻
- 故障时是否有工序正在加工

#### A2：多机器同时故障

多台机器在同一时刻发生故障。

除了处理多个受影响任务，还需要检查剩余工序是否仍有可用候选机器。

#### A3：多机器连续故障

不同机器在不同时间先后发生故障。

系统可能在前一次重调度尚未执行完成时再次触发重调度，因此需要保存每次事件后的最新系统状态。

### 3.3 受影响任务

故障时任务分为：

1. 故障前已经完成的任务：冻结。
2. 故障时正在故障机器上加工的工序：按照中断规则处理。
3. 原计划分配给故障机器但尚未开始的工序：重新分配或等待维修。
4. 其他机器上尚未开始的工序：局部优化时尽量保持，全局重调度时允许调整。
5. 已开始或等待执行的 AGV 运输任务：根据目标机器是否改变进行保留或重新安排。

## 4. 课题 B：订单撤销

### 4.1 研究问题

原调度方案执行期间，某个订单被撤销时，如何停止与该订单相关的后续加工和运输，并利用释放出的机器与 AGV 资源优化剩余订单。

### 4.2 撤销场景

订单撤销初步分为三个子问题：

```text
B1：尚未开始加工的订单撤销
B2：正在加工的订单撤销
B3：已经完成部分工序的订单撤销
```

后续可以扩展：

- 单订单撤销
- 多订单同时撤销
- 多订单在不同时刻连续撤销

### 4.3 受影响任务

订单撤销时需要识别：

1. 被撤销订单已经完成的工序记录。
2. 被撤销订单正在加工的工序。
3. 被撤销订单尚未开始的加工任务。
4. 被撤销订单尚未开始或正在执行的 AGV 运输任务。
5. 因资源释放而可以提前执行的其他订单任务。

订单撤销与机器故障的区别是：

- 机器故障减少可用资源，但订单仍需完成。
- 订单撤销减少待完成任务，并释放机器与 AGV 资源。

## 5. 通用重调度策略

两类动态事件使用同一组策略层，便于对比。

### 5.1 直接修复基线

不运行完整优化算法，只进行满足可行性的最小调整。

- 机器故障：等待维修或将受影响工序顺延。
- 订单撤销：删除被撤销订单的未执行任务，其他计划保持不变。

该策略用于提供最简单的实验基线。

### 5.2 局部优化

只优化事件直接影响的任务以及必要的关联任务，尽量保持原计划稳定。

- 机器故障：主要调整故障机器上的中断和未开始工序。
- 订单撤销：利用被释放的局部时间窗口调整相关机器和 AGV 上的任务。

### 5.3 全局重调度

冻结事件发生前已经完成的任务，对事件发生后的全部剩余任务重新优化。

允许重新决定：

- 工序执行顺序
- 候选机器选择
- AGV 分配
- AGV 速度选择

## 6. 场景与策略组合

每个事件场景都可以分别使用不同策略：

```text
事件场景 × 重调度策略
```

例如机器故障实验：

| 场景 | 直接修复 | 局部优化 | 全局重调度 |
|---|---:|---:|---:|
| 单机器故障 | 是 | 是 | 是 |
| 多机器同时故障 | 是 | 是 | 是 |
| 多机器连续故障 | 是 | 是 | 是 |

订单撤销实验也采用相同的对照结构。

因此，“三个机器故障子问题”和“两种或三种重调度策略”不是互相替代，而是进行组合实验。

## 7. 两个课题共享的处理流程

```text
生成正常调度方案
→ 调度执行到事件时刻
→ 接收动态事件
→ 提取当前系统状态
→ 识别冻结任务与受影响任务
→ 构造剩余调度问题
→ 选择重调度策略
→ 生成新调度方案
→ 检查可行性
→ 评价并与原计划比较
```

### 7.1 公共系统状态

两个课题共享的状态至少包括：

```matlab
state.current_time
state.completed_operations
state.processing_operations
state.remaining_operations
state.job_ready_time
state.job_position
state.machine_status
state.machine_available_time
state.agv_status
state.agv_available_time
state.agv_position
state.agv_energy
```

事件特有信息单独保存：

```matlab
event.type
event.time
event.machine_ids
event.repair_end_times
event.cancelled_job_ids
```

## 8. 评价框架

### 8.1 效率指标

- 最大完工时间
- 平均订单完成时间
- 机器利用率
- AGV 利用率

### 8.2 能耗指标

- 机器加工与空闲能耗
- AGV 运输与充电能耗
- 总能耗

### 8.3 稳定性指标

- 工序开始时间变化
- 工序机器分配变化
- AGV 分配变化
- 被调整工序数量

### 8.4 响应能力指标

- 重调度算法运行时间
- 事件发生到新方案生成的响应时间
- 无可行候选机器的工序数量

## 9. 建议的代码架构

```text
src/
├── data/                 正常问题数据读取
├── scheduling/           正常调度基础接口
├── events/
│   ├── machine_fault/    机器故障事件
│   └── order_cancel/     订单撤销事件
├── state/                事件时刻系统状态提取
├── residual/             剩余调度问题构造
├── rescheduling/
│   ├── direct_repair/    直接修复基线
│   ├── local/            局部优化
│   └── global/           全局重调度
└── evaluation/           效率、能耗、稳定性和响应评价
```

架构原则：

1. 事件类型与重调度算法分离。
2. 机器故障和订单撤销共享状态提取与评价接口。
3. 不为每个场景复制一套完整算法。
4. 先实现单事件、小样本，再扩展多事件。

## 10. 研究实施顺序

### 第一阶段：总架构和公共定义

1. 明确机器故障与订单撤销两个大课题。
2. 定义统一事件结构。
3. 定义统一系统状态。
4. 定义冻结任务、受影响任务和剩余任务。

### 第二阶段：机器故障基础场景

1. 单机器故障。
2. 直接修复基线。
3. 局部优化。
4. 全局重调度。

### 第三阶段：机器故障扩展场景

1. 多机器同时故障。
2. 多机器连续故障。

### 第四阶段：订单撤销基础场景

1. 尚未开始订单撤销。
2. 正在加工或部分完成订单撤销。
3. 直接修复、局部优化与全局重调度对比。

### 第五阶段：综合实验

1. 统一小样本测试。
2. 不同事件强度对比。
3. 不同重调度策略对比。
4. 完工时间、能耗、稳定性和运行时间分析。

## 11. 当前边界

当前只建立研究架构，不立即实现所有场景。

下一项小任务应当是定义统一的 `event` 和 `state` 数据结构，使机器故障与订单撤销能够进入同一套重调度流程。
